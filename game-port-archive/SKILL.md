# 游戏移植收藏归档

目标：让用户以后按“看中文说明 → 解压选定包 → 提供自有镜像/ROM或按向导导入”就能玩。做不到这一步的项目，明确标成“需构建”“需本地生成”“联网安装器”或“浏览器版”，不把源码、安装器或更新包说成现成游戏。

## 范围

- 负责本地合集的整理和更新，以及本地与用户选定的一个云盘目录（百度网盘或 Google Drive）之间的上传、下载和核对。不做云盘之间的复制或迁移，不经 VPS 中转。
- 合集位置、选定云盘、哪一边是主库、传输方向，读取用户 LOCALAPPDATA/GamePortArchive 中的本机连接记录。找不到时向用户确认，不猜路径或账户。
- 商业游戏本体、ROM、ISO、BIOS、密钥由用户自备，不代为寻找。归档过程中不执行下载来的游戏、安装器或 APK。
- 用户说“先看看”时只做筛查并汇报，不下载、不上传。否则每个项目要做到本地验收和云盘发布才算完成；只查了上游或列了计划不算完成。
- 用户说“先处理这些链接，再检查其他已有项目”时，先把指定批次做完（包括云盘发布），再对其余收藏和观察名单走同一流程，最后合并汇报。
- 单个项目受阻时保留它的旧资源，记录具体缺口，继续做不依赖它的项目。

## 拿到链接后先分流

1. 清掉链接里夹带的中文标点。链接是游戏目录页时，追溯到实际的代码仓库。
2. 以规范仓库地址（GitHub 为 owner/repo，其他托管站带上站点）作为项目身份，在项目记录和观察名单里查重。仓库改过名或转移过的，按跳转后的地址比对，并在记录里保留旧地址。
3. 按查到的情况处理：

| 情况 | 处理 |
|---|---|
| 已收藏 | 和上游比较，有变化才更新，无变化不重下 |
| 在观察名单里 | 重新读可玩性依据；达标就晋级为收藏，未达标只更新检查日期 |
| 新项目，达到可玩标准 | 新建本地项目 |
| 新项目，未达标 | 记入观察名单，不下载任何资源 |
| 访问受阻，或上游已消失 | 记录证据；已收藏的保留现有归档，不删除 |

- 同名游戏的不同移植是不同项目，分别建档。同一仓库包含多个游戏时算一个项目，保留所有游戏入口，资源只存一份。关联依赖不算主项目。
- 用户只给一批链接时，只处理这批和与它相关的观察项。用户要求同步全合集或复查观察名单时，才复查整个观察名单。
- 可玩标准见[可玩性判定](references/archive-contract.md#可玩性判定)，没有现成运行包的项目见[需自行构建的项目](references/archive-contract.md#需自行构建的项目)，观察名单的格式和状态见[待观察项目](references/watchlist.md)。

## 选包规则

- **作者提供了可以直接运行的成品时，把成品下载回来。**
- **每个平台只留一个最新适用版本。** Windows 优先 x64，没有 x64 才留 x86。Android 默认 arm64-v8a，细则见 [Android 规则](references/android.md)。两个平台分别判断，互不覆盖。仅主机（Xbox、PS5 等）目标不下载。
- **额外的包要有理由。** 只有新版覆盖不了的地区、功能、图形后端或稳定路径，才多留一个包，并在说明里写默认选哪个、为什么。便携 ZIP 优先。稳定版和实验版之间看功能、地区、限制和作者建议来选。
- **架构以文件内容为准。** 看 PE 头或 APK 内的 ELF，不信文件名。必需的 32 位辅助工具不算另一个 32 位游戏版本。
- **判断上游有没有更新，要分别比较**源码提交、发行标签、附件 ID、附件名、大小、更新时间和可用的摘要。作者会在同一个标签下重传附件，所以不能只看标签；也不能只看仓库更新时间。发行列表按需翻页。作者把发行迁到别的平台时跟过去，不把 GitHub 上的旧包当成最新。
- **依赖分两类。** 通用环境（Python、Git、VS、CMake、Rust、JDK、驱动等）只在说明里写要求，不下载。运行包自带的 DLL、资源、工具、运行时和许可证完整保留；项目专用的框架、固定编译器、补丁、配套引擎要保全，多个项目共用的集中压缩存放。
- **源码锁定完整提交**，补齐专用子模块和 LFS 文件，不能只留不含子模块的 source.zip。做法见[源码保全](references/archive-contract.md#源码保全)。用户明确不留源码的项目记 source_preserved=false，以后更新不自动补回；Reignition 已按此处理。
- **沿用已有决定。** 已收藏项目的平台、版本取舍和目录名，不因规则调整而自动重下或改名。

## 执行步骤

1. **查本地。** 从项目顶层的项目记录、manifest、观察名单、校验表和实际文件建立基线。历史快照里的记录不是当前项目。记下本轮范围、原版本和已知缺口。本地缺文件不等于云端也缺。
2. **查上游。** 读 README、发行说明、构建和游戏文件文档、`.gitmodules`、`.gitattributes`。按上面的分流和选包规则，把每个项目定为新增、更新、无变化、观察或访问受阻；源码、运行包和各平台分别判断。检查时间同时记 UTC 和用户本地日期。连不上时不声称确认了最新。
3. **核对云端。** 每批首次写入前和中断续传前，核实本机服务进程、项目绑定的账号和真实目标目录，再读取本轮相关的云端记录和目录。云端与本地记录不一致时，先比较版本、哈希、检查时间和用户修改，保留差异再合并，不用本地盲目覆盖。只在首次同步、用户要求全量同步或发现一致性问题时才审计整个云端。见[百度网盘](references/baidu-openlist.md)、[Google Drive](references/google-drive.md)。
4. **下载。** 放在合集外的暂存区，先写成 .part，核对大小和可用的上游摘要后再改名。记录原 URL、大小、本地 SHA256 和实际核对过的上游摘要。同名附件的摘要变了就不复用旧缓存。
5. **整理打包。** 补齐源码子模块；配齐必需的配套文件，例如同架构、同分支的引擎；错标格式的包转成真正的 ZIP。不修改上游源码，不自己给游戏加版本号。目录按[命名与改名](references/archive-contract.md#命名与改名)建立。最终只留压缩包，展开目录在确认压缩包已覆盖其内容后清除。
6. **写说明和记录。** 中文说明按[中文说明](references/archive-contract.md#中文说明)的要求写。项目记录是权威数据，manifest、校验表、CSV、HTML 目录和统计都从同一批项目记录生成。合集只保留一份综合说明，不逐轮追加版本对比或验收文档。
7. **本地验收。** 逐文件 SHA256、ZIP CRC、打包后读回比对，再运行验收脚本。检查当前说明里的链接没有死链，清单只引用真实存在的文件，没有残留的 .part 或展开目录。
8. **发布到云盘。** 顺序固定：先上传新包并回读验证，再发布项目说明和记录，最后更新中央清单和目录。上传成功不等于已验证。中途失败时保留旧版和进度，按[中断后续传](references/verification.md#中断后续传)逐文件续作。没有使用云盘时跳过这一步。
9. **清理。** 新包和记录全部验收后，删除明确被替代的旧包，不另建备份区，历史只留来源和哈希。删除前确认绝对路径在目标合集内，且没有混入用户的存档和数据。新版缺资源，或地区、功能有退化时，保留旧包并说明原因。不对不完整的暂存目录运行删除型同步，也不根据云端与本地的差集删除未管理的文件。
10. **汇报。** 用中文简报：哪些无变化、新增、更新、观察、受阻；保留的版本和架构；需要用户自己做的操作；合集路径和大小；上传和回读的范围。静态校验、上游摘要核对、云端一致性和游戏实测分别说明，互不替代；没有实测就写未实测。

验收的完整要求和脚本覆盖不到的检查见[验收规则](references/verification.md)。目录结构、记录字段和真实案例见[归档结构与验证约定](references/archive-contract.md)。

## 脚本

```text
python scripts/archive_tools.py inspect FILE [--crc]
python scripts/archive_tools.py pack SOURCE_DIR OUTPUT.zip --prefix source
python scripts/verify_archive.py 合集目录 [--cloud-listing cloud-files.json]
```

- inspect 识别文件的真实格式和 PE 架构。它不检查 APK 内的 ELF，Android 架构需另行核对。
- pack 逐文件计算 SHA256 后打包并读回比对。它不覆盖旧文件、不删除输入，先在暂存区运行。
- verify_archive 只读核对项目记录、中央清单和实际文件。输出 ok=false 或退出码非零时不能当作已验收。`--cloud-listing` 只接受 rclone 导出的带 SHA256 的清单；百度网盘没有这种清单，按百度文档下载回读核对。
