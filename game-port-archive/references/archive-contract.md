# 归档结构与验证约定

适配现有合集，不硬编码主项目数、当天目录或发行标签。

```text
合集/
  打开目录.html、合集说明.md、待观察项目.md
  Game Official English Name - Author/
    中文说明.md、项目地址.url、项目记录.json
    源码_含专用子模块.zip
    运行包/选定ZIP或APK
    发行源码/必要的发行对应源码或许可材料
  _专用工具/共享专用工具ZIP + 中文说明
  _归档记录/
    当前管理记录/manifest.json、校验结果.json、待观察项目.json
      项目总表.csv、下载文件SHA256.csv、版本取舍清单.json
      归档统计.json、体积分析.json
    历史记录.zip（迁移时一次合并的旧材料）
    历史_YYYY-MM.zip（以后按月留档，有必要证据时才创建）
```

## 精简记录约定

- 项目顶层 `项目记录.json` 是当前状态权威；manifest、校验表、CSV、索引和统计从同一批记录生成。观察项目由当前管理目录中的待观察清单维护。
- 用户只需总入口、合集说明和游戏中文说明。当前目录不保存逐轮副本。
- 历史仅保留版本/提交变更、来源链接、归档哈希、必要改名映射和特殊处理原因，去重后按月压缩。无需保存完整旧manifest、旧HTML/CSV索引、重复报告、临时脚本、全量API响应或嵌套原始证据包。无法从结构化记录还原的异常原因保留简短原文及出处。
- 精简已有历史先检查引用，提取需保留字段和原因；验证新ZIP的记录与读回内容后替换，不把原历史另搬到备份区冒充精简。历史来源字段可保留原档案内路径作为追溯标识，须说明不是当前文件链接。
- 新版及记录全部验收后直接删除可替代旧包，不另建“可恢复区”或旧版备份。平台服务自带回收站不必主动清空；需要旧版本时按历史来源回上游获取。新版缺必要资源或不覆盖原有地区/功能时，先保留仍必要的版本并解释。
- 云端主库先上传并读回验证精简历史及更新说明，再清理明确废弃项；更新统计，游戏/源码归档内容不变。用户ROM、存档和额外文件不动。


项目记录至少包括规范仓库URL、检查时间、分支、40位提交、运行版本/真实架构、相对文件路径、大小、SHA256、原URL、原包哈希、重打包来源、版本取舍与依赖缺口。源码和二进制分别记录版本。零发行、需登录的工件、下载失败不能都写成“无更新”。

## 中文说明

先写将来的最少操作：

- 选哪个ZIP、解压后的准确入口；完整便携包/更新包/安装生成器/浏览器包，是否需联网/首次编译。不要把“拖到EXE”“启动器选取”“放特定目录”“解密提取后生成”统称成“扔进去就行”。
- 原版地区、平台、序列号/Title ID、修订/补丁、BIOS、ISO/ROM/Data.rsdk等格式和目录。商业游戏本体、密钥不从第三方站点代下。
- 通用环境及版本；专用文件的保存位置。多包的默认选择、不可互替原因；有依据的存档/设置路径及更新备份方法。
- GitHub、迁移后的官方下载页、已选版本/源码SHA、检查日期。源码ZIP内部文档应写“解压后查看source/...”，不要生成指向不存在展开路径的点击链接。
- 静态校验与真实运行分开写。没有游戏数据时明确未实测，不写“已验证解压即玩”。

## 已有收藏的真实案例

- 某包标windows-x64.zip，实际为RAR5且EXE为x86。按魔数和PE头识别，无损转标准ZIP，只有32位时仍保留，不能改名伪装64位。
- RSDKv3/v4架构包二选一；Sonic Mania发行可能只有Game.dll，须配同版本、同分支、同架构RSDKv5引擎。默认v5U，同版本v5兼容分支可放同一ZIP。
- Skies常规版支持美欧日，而新性能版仅美版，不可替掉常规版。X6合作实验版不等于作者保留的稳定单人路径。SDOJ图形后端可以作为同版兼容备选，写明真实差别。
- CPS2多个EXE是不同游戏，不是重复；源码14项不意味着发行包也有14个入口。
- 中日文update包可能只给已有安装，不能代替首次生成。内嵌Updater.exe与单独下载逐字节相同时可去重。
- 便携版优先便于集中管理，但存档位置按上游确认。README迁移发行平台后继续追溯，受限时明确旧包回退而非声称最新。
- WASM包不适用PE架构筛选，保留HTTP服务器及所需COOP/COEP、Range支持。项目Wiki不等于公开可玩网址。
- 需自有ISO生成代码的安装器不是已生成游戏。安装器的PE架构不代表最终游戏架构；不为归档执行它或下载大套通用工具。

## 命名与改名

- 目录名为“游戏正式英文名 - 项目特征后缀”，不挂数字。后缀取移植项目名或作者，需要时再加平台或不可互替版本。新建项目一律带后缀，同一游戏以后出现别的移植时不必改名。仓库名不等于游戏名。
- Windows禁用字符用连字符替换。多游戏项目以正式游戏名称组合命名。
- 改名先建立并验证一对一映射，检查重名和目标路径，保留可回查映射；更新当前manifest、CSV、HTML、说明与哈希清单路径。历史快照保持原样并注明旧路径。现有目录不因新规则自动改名。

## 可玩性判定

- 新增或更新前，同时核对游戏页面描述与GitHub README、发行说明中的可玩状态。不能仅凭目录站Playable标签或仓库有Release判定可玩。
- 仅建仓、刚开工、只能启动/菜单、严重缺陷导致无法正常游玩的项目登记为待观察，只保留仓库链接、页面地址、状态依据和检查时间，不下载源码/运行包/专用资源。登记格式见[待观察项目](watchlist.md)。
- Alpha/Beta不自动排除，也不因Alpha标记自动跳过更新，依据实际玩法支持判断。稳定/实验选择看功能、地区、限制和作者建议。
- 已收藏但不再满足条件的项目跳过资源更新，不擅自删除原收藏。
- 没有现成EXE或Release附件不构成排除理由，按下节收录。不要把“尚未编译验证”写成“不可玩”，也不能把作者可玩记录说成本机实测。

## 需自行构建的项目

- 已有可玩依据且项目给出明确构建、导入或本地生成流程时收录：保全固定源码、专用工具/补丁/资源及完整中文步骤，明确标注“需构建”“浏览器版”或“需本地生成”。通用编译环境只说明；用户自备ROM、ISO、BIOS与商业素材不代为寻找。
- 无二进制发行时，核对作者构建目标和输出文件；源码本身就是安装/构建输入，可合为一份构建收藏ZIP，避免再存内容相同的源码包。
- 说明在哪个系统构建、工具版本/通用依赖、用户素材放置位置、构建命令、启动方式、联网需求及尚未验证边界。
- 网页构建完成后可在Windows浏览器使用，不要因wasm32或Linux构建流程误当成另一套Windows x86发行。

## 重打包与更新判定

- 上游附件与收藏ZIP分开记录：原附件ID、updated_at、字节数、SHA256用于查重传；收藏包自己的字节数和SHA256用于交付。合并配套或EXE转ZIP后，两者不同是正常现象，不能直接比较后判为上游更新。旧记录缺原包字段时，可核对原始来源记录；必要时用当前官方附件的逐文件哈希确认已包含在原完整配套内，不能为补元数据把现成配套换成不完整原包。
- 包的用途结合发行说明和包内入口判断，仓库名或文件名包含Source不等于源码。运行附件仍归运行包；原有不可替代工具、字体、脚本按新版本重新核对。上轮的“配套验证通过”标志不能直接继承给新的运行包。
- 当前记录里的旧提交验证结论、运行方式和检查状态随更新重写，派生索引从更新后的同一记录生成。固定依赖404时不偷换新提交；允许先更新可独立使用的发行包并保留上次完整源码，但必须分别记录二进制版本、实际保存的源码提交、观察到的新提交及缺口，不称新源码完整。

## 完整性与恢复

- 大型源码下载中断时，不把能列出部分内容的ZIP当完整包。可用官方未截断的固定提交Git树逐项核对大小及Git blob SHA1，仅补缺失对象，最后验证全树再重打包。Windows checkout可能转换换行；若哈希不符，应读取同一提交原始blob，不擅自接受转换后内容。这个恢复路径须保存固定树、验证统计与传输错误证据。
- 本地哈希证明比对一致；只有真正核对作者SHA或GitHub digest才写“上游校验通过”。
- 重打包读回每个文件并比对SHA256，保留路径、必要空目录、许可证和内部清单。原ZIP覆盖检查防止遗漏；LFS/失效子模块缺口如实保留。
- 源码里合法存在的.git也可保全。清除已校验原目录中的只读Git对象时，仅清这些目标对象的只读属性，不扩大删除范围。
- 先下载/验证新包再删除旧包。有新包资源缺失、地区支持退化时保留旧包并解释。存档和用户数据另备份。
- 增量需要每项目状态；恢复时不把历史项目记录当当前项目，不重复覆盖已完成记录。报告先生成再验链接。

当前合集采用单一合集说明.md；机器记录集中于_归档记录/当前管理记录。读取当前manifest等应先定位真实路径。Reignition不再保存源码，更新时沿用该项目的source_preserved=false。
