# 游戏移植收藏归档

目标：让用户以后按“看中文说明 → 解压选定包 → 提供自有镜像/ROM或按向导导入”操作。做不到时明确标成研究源码、需本地生成、联网安装器或浏览器包，不把源码/安装器/更新包说成现成游戏。

## 可玩性与命名规则（2026-11-09更新）

- 从游戏目录页追溯GitHub，按规范owner/repo去重；多个游戏可共用同一个仓库，保留所有适用游戏入口，不重复下载相同归档。
- 新增或更新前，必须同时核对游戏页面描述与GitHub README、发行说明中的可玩状态。仅建仓、刚开工、只能启动/菜单、严重缺陷导致无法正常游玩的项目，先登记为待观察，仅保留仓库链接、页面地址、状态依据和检查时间，不下载源码/运行包/专用资源；不能仅凭目录站Playable标签或仓库有Release判定可玩。Alpha/Beta不自动排除，依据实际玩法支持。已有但不满足条件的项目跳过资源更新，不擅自删除原收藏。按本轮范围复查相关待观察条目，确认出现可玩PC/Android版本或明确可玩构建流程后再晋级下载，沿用同一仓库身份去重。历史删去或跳过的项目可从记录恢复链接，不自动恢复资源；仅主机目标单独标记，不冒充待发布PC/Android移植。
- 没有现成EXE或Release附件不构成排除理由。已有可玩依据且项目给出明确构建、导入或本地生成流程时，也应收录：保全固定源码、专用工具/补丁/资源及完整中文步骤，明确标注“需构建”“浏览器版”或“需本地生成”。通用编译环境只说明；用户自备ROM、ISO、BIOS与商业素材不代为寻找。不要把“尚未编译验证”写成“不可玩”，也不能把作者可玩记录说成本机实测。
- 主游戏目录以游戏正式英文名称开头，不挂数字。作者、平台、移植项目或不可互替版本放末尾后缀；Windows禁用字符用连字符替换。多游戏项目以正式游戏名称组合命名。仓库名不等于游戏名。
- 改名先建立并验证一对一映射，检查重名和目标路径，保留可回查映射；更新当前manifest、CSV、HTML、说明与哈希清单路径。历史快照保持原样并注明旧路径。
- 只保留一个最新适用运行版本，优先Windows x64、无x64则x86；不可互替例外保留并解释。用户明确不保留某项目源码时，记录source_preserved=false，后续更新不得自动补回。Reignition已按用户要求仅保留运行包。
- 沿用合集当前位置和已有单一综合说明，不再追加多份重复的版本取舍、前后对比和验收文档。机器索引与CSV集中在_归档记录/当前管理记录；以每项目记录为权威数据生成派生视图。当前说明直接更新，不逐轮追加；历史按月精简压缩，具体见[精简记录约定](references/archive-contract.md#精简记录约定)。

## 平台范围（2026-11-10起）

- 同时收录PC和Android，按平台分别保留一个最新适用版本；Windows x64优先、仅x86时保留x86。Android优先设备适用ABI（默认arm64-v8a），保留上游APK及必要配套，不以Windows包覆盖Android包，也不下载同平台可替代旧版。
- 仅Xbox/PS5等主机目标仍不下载。此前删除或跳过的Android资源不追溯补齐；本次及以后新提交或明确要求更新的Android项目按新规则处理。
- Android说明须列最低系统、ABI、GPU/Vulkan、内存/空间、安装/导入步骤、首次本机生成耗时、用户自备游戏格式及备份边界。用APK内ELF核实架构，不能套用PE判断；不在归档过程中安装或执行APK。拆分APK/APKS/XAPK须说明安装器和必需分包，不能假称单APK即装即玩。
- 运行包附带的专用生成器/编译器保留；通用SDK、JDK等只写要求。文件夹仍以正式英文游戏名开头，Android可作尾缀。合集现有路径不因增加Android自动改名。

## 收藏规则

- 沿用已有合集，先按GitHub `owner/repo` 去重、查当前记录；清除复制链接附带的中文标点并记下修正。关联依赖不另算主项目，同名游戏的不同移植不合并。
- 实时读取默认分支、完整提交、相关发行和作者说明；分别比较上次源码SHA、运行标签、附件ID、附件名、大小、updated_at及可用的GitHub digest/作者校验值。作者可能在原Release Tag下重传附件（如VF1/2/3），绝不能仅看tag判断无变化。无变化不重下；不能只凭仓库更新时间判断程序更新。发行列表按需翻页。
- Windows优先x64；只有32位现成包时按相同规格保留x86。核对EXE及DLL的PE头，不信文件名。必需32位辅助工具不等于另一个32位游戏版本。
- 一般只留一个最新适用版本，便携ZIP优先。不要因Alpha标记自动跳过更新；稳定/实验选择看功能、地区、限制和作者建议。只有不能覆盖的地区、功能、后端或稳定路径才保留额外包，说明默认选择及原因。Android新版本号不等于Windows更新。
- 最终只留压缩归档，清除已保全的展开目录。源码要纳入已经补下的专用子模块，不能仅留最初不含子模块的source.zip。中文说明、更新快捷方式、当前文件记录放在外面，旧路径记录归入历史。
- 通用Python、Git、VS、CMake、Rust、驱动等只说明要求，不额外下载。上游运行包自带的DLL、资源、工具、运行时及许可证完整保留。项目专用框架、固定编译器、特殊补丁/配置、配套引擎等另行保全；共享专用工具集中压缩。

## 执行流程

1. **本地盘点，建立基线。** 先读本机连接记录确认主库和合集位置；只盘点当前项目顶层记录、manifest、待观察清单、已有校验记录及相关实际文件，不递归把历史快照当项目。按规范 `owner/repo` 去重，保留既有平台取舍和 `source_preserved=false` 等用户决定。记录本轮范围、原版本/提交、已有文件、缺口和必要旧记录；本地缺文件不等于云端也缺。没有本地记录时才从主库获取所需记录。此步先于云端枚举和资源下载。
2. **上游核对，形成增量清单。** 读README、发行/构建/游戏文件文档、资源清单、`.gitmodules`、`.gitattributes`和必要脚本。发行迁移时跟随作者的新平台链接，不能把GitHub旧包充当全网最新。连接受阻时记录证据、保留官方地址，继续独立可做部分。 无网络时不声称确认了最新。按发行与可玩性规则，逐项分为新增、更新、无变化、待观察或访问受阻；分别判断源码、运行包、平台和依赖。无变化不重下，不把同版本附件重传漏掉。用户给定项目批次只处理该批及相关观察项；明确要求同步全合集时才复查完整观察名单。检查时间同时保留 UTC 和用户本地日期。观察规则见 [观察名单约定](references/watchlist.md)。
3. **云端定向复核，解决漂移。** 云端为主库时，读取本轮相关项目记录、中央 manifest 及目标目录；本地信息只作基线，不证明远端当前状态。记录不一致时先比较版本、哈希、检查时间和用户修改，保留差异再合并，不盲目用本地覆盖远端。完整 manifest 的一致不能代替相关文件存在性检查。首次迁移、明确全量同步或发现一致性问题时才扩大到全库审计。只读筛查无需开展上传验收。
4. **暂存下载。** 源码锁定完整SHA；附件保留原URL、大小、本地SHA256和实际核对过的作者校验/GitHub digest。下载用.part，成功才原子更名。同名附件哈希改变时不能复用旧缓存。 缓存按仓库与完整提交、或附件ID/updated_at/digest识别；共享依赖按同一仓库与SHA复用，避免并发重复下载。大型源码更新可先用旧归档逐文件匹配新提交的Git blob，仅补变化文件；旧文件若有CRLF转换，只有还原后的字节重新匹配目标blob时才可复用，不能只凭文件名或“看起来一样”判定。不要为归档执行下载的游戏/安装器。
5. **补齐再压缩。** 先固定父项目完整提交，再按该提交的gitlink SHA递归补齐所需专用子模块，记录仓库、路径、SHA及验证结果。允许固定提交ZIP加补齐子模块，或克隆后checkout指定父提交、执行submodule sync/update --init --recursive；不能只克隆默认分支就声称固定版本。禁止把未补齐的GitHub源码ZIP称为完整包；失效提交不得替换成最新版。通用依赖按既有规则说明，必要固定依赖保全。核验并保存提交来源后再移除暂存.git元数据；识别LFS指针，补真实文件或记录缺口。保留许可证，用archive_tools.pack或等价方式打包并读回校验。
6. **准备最少操作路径。** 缺Game.dll/配套引擎则配好同架构同分支；错标RAR等转真正ZIP。保留所有必需文件和来源，可附中文使用说明。优先上游启动/本地服务器脚本。浏览器包、需镜像生成的安装器、联网依赖要明确；没有用户游戏数据时不能凭空生成最终游戏。
   无二进制发行时，核对作者构建目标和输出文件；源码本身就是安装/构建输入，可合为一份构建收藏ZIP，避免再存内容相同的源码包。说明在哪个系统构建、工具版本/通用依赖、用户素材放置位置、构建命令、启动方式、联网需求及尚未验证边界。网页构建完成后可在Windows浏览器使用，不要因wasm32或Linux构建流程误当成另一套Windows x86发行。
7. **本地验收，准备发布。** 用 `scripts/archive_tools.py pack` 或等价方法逐文件SHA256、打包后读回比对及CRC检查。原source.zip与合并归档另核对覆盖；有差异保全原包。新包验证后生成同一批项目记录及派生索引，当前说明重写为单一现状，版本号、完整文件名和包内入口取自当前记录，不累加旧版本段落或用无边界的前缀替换；云端主库发布完成前保留恢复所需旧包与记录，清理留到下一步。确认删除绝对路径在目标合集内，且没有混入用户存档/数据。不把文件搬到别处冒充节省空间。
8. **发布、云端验收与清理。** 写入前再次确认相关远端记录未被并发修改；先上传新包并验证，再发布项目记录和派生索引，读回核验后直接删除明确被替代旧包，不另建旧包备份或可恢复目录，需要旧版时按历史来源回上游获取。没有云端主库时，在本地验收后替换。上传失败或校验不一致时保留旧版与进度，不把已上传写成已验证；继续独立项目，恢复时以文件哈希和已完成证据续作。更新中文说明、HTML索引、CSV、manifest、当前SHA清单、版本取舍和审计/体积统计。先生成报告再检查链接；主项目数一致，当前清单只引用真实文件，无.part或展开目录。旧URL、哈希、缺口留在历史区。增量只验新增/改变归档，除非出现新完整性疑点。交付前核对实际文件、项目记录、中央校验表、manifest与SHA清单一致，源码提交与来源URL一致；检查当前说明死链。涉及云端时按明确的管理范围比对相对路径集合、重复路径、逐文件大小和可用哈希，缺少哈希不能称为完整验证；暂存文件和用户额外文件单独说明，不据差集擅自删除。具体门禁与脚本边界见[验收规则](references/verification.md)。

结构、中文说明要求、实际案例和报告边界见 [references/archive-contract.md](references/archive-contract.md)。需要打包或识别架构时：

```text
python scripts/archive_tools.py inspect FILE [--crc]
python scripts/archive_tools.py pack SOURCE_DIR OUTPUT.zip --prefix source
```

脚本不覆盖旧文件、不删除输入，生成内部逐文件清单和外部验证记录，先在暂存区运行。归档不修改应用源码或上游版本，不人为给游戏加版本号；另行开发应用功能时遵守其版本规范。

交付简报用中文：已有无变化/新增/更新、保留版本及架构、额外操作和未验证边界、合集实际路径/大小。

## Google Drive维护

- 用户选择云端为主库后，先读取本机连接记录中的remote、root_folder_id与配置位置；授权令牌只在本机专用目录，绝不上传合集或提交GitHub。根目录限定是操作范围，不等同OAuth权限范围。
- 本会话连接线索：用户LOCALAPPDATA/GamePortArchive 中的连接记录；维护脚本在 D:/projects/game-archive-maintenance。未找到配置时重新确认连接，不能猜测账户或云端目录。
- 首次迁移按相对路径比对全部文件数量、大小和可用哈希，排查Drive同名重复；浏览器上传完成提示不足以证明完整。未核验完成不删除本地原件。
- 后续维护遵循上述执行流程：本地盘点和上游增量判断在先，云端定向复核在后；新包上传核验、记录发布核验完成后，再处理被替代旧包。禁止以不完整本地暂存目录对整个云端运行删除型sync。
- 全集不必回下载；旧包使用既有校验记录与远端哈希。新版验收后直接删除可替代旧包，不另存旧包备份，用户自有ROM、存档和额外文件不动。上传成功与校验完成分别记录。
- 云端接入以实际列目录及小型审计记录上传读回为验证；未验证不能报告读写可用。共享OAuth客户端可能停用，失效时改用用户专用客户端，勿称其永久有效。
